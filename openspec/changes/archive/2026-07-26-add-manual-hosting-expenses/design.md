## Context

Расходы попадают в `expenses` только через импорт CSV (`app/server/imports/index.ts`) и вебхук телефонии (`app/server/expenses/gudok-history.ts`, `TELEPHONY_TYPE = 'telephony'`). Оба используют идемпотентную логику: найти по `(date, siteId, type)` → обновить сумму, иначе вставить. Таблица `expenses` хранит `amount` в копейках, `type` — свободная строка, есть уникальные индексы `(date, siteId, type)` и `(date, type)` для `siteId IS NULL`.

Существующая кнопка «Добавить» в доходах (`AddRevenueModal` + `finance.tsx`) — **клиентская**: добавляет строку в `localAdds`, в БД не пишет (комментарий «Old behavior parity»). Для хостинга так не годится: годовой платёж должен сохраняться.

## Goals / Non-Goals

**Goals:**
- Кнопка «Добавить» на вкладке расходов (визуально как в доходах), доступная только администратору.
- Модалка: выбор **года**, сайта (или «Общий»), суммы; тип зафиксирован `hosting`.
- Реальное сохранение в `expenses` через серверный `action` с upsert-семантикой (как импорт/вебхук).
- Дата = `YYYY-01-01`, идемпотентность по `(date, siteId, type)`.

**Non-Goals:**
- Редактирование и удаление расходов в UI (пока нет).
- Другие типы расходов в модалке — структура допускает расширение позже, но сейчас только хостинг.
- Изменение схемы БД / миграции.
- Persist-переделка добавления доходов (остаётся клиентским, как было).

## Decisions

- **Серверный `action` в `finance.tsx`, а не клиентский add.** В отличие от доходов, хостинг должен сохраняться. `action` вызывает `requireAdmin`, парсит форму (`intent=add-hosting`), пишет в БД, затем UI ревалидируется (`useRevalidator`/`useFetcher`). Альтернатива — отдельный resource route; отклонено, т.к. вкладка расходов уже живёт в `finance.tsx` и там же loader.
- **Выбор года вместо даты.** Хостинг оплачивается раз в год; поле — `YearSelect` (год) → дата `YYYY-01-01`. Проще для пользователя и ложится на уникальный индекс (одна запись hosting на сайт в год).
- **Upsert по `(date, siteId, type)`.** Переиспользуем существующую логику совпадения из импорта: если запись есть и сумма та же — no-op; если другая — update; иначе insert. Выносим общий хелпер в `app/server/expenses/` (напр. `upsertExpense`), чтобы не дублировать. Константа `HOSTING_TYPE = 'hosting'` рядом с `TELEPHONY_TYPE`.
- **Модалка `AddHostingModal` по образцу `AddRevenueModal`.** Та же структура (Modal + form + Input/Select + кнопки), но дата → `YearSelect`, тип скрыт и захардкожен. Спроектирована с прицелом на будущие типы (сейчас только hosting).
- **Права.** Кнопка рендерится при `isAdmin`; сервер защищён `requireAdmin` независимо от UI.

## Risks / Trade-offs

- **Тихая перезапись суммы при повторе за тот же год** → приемлемо и ожидаемо (как импорт); показываем результат «создано/обновлено» в уведомлении, чтобы не было сюрприза.
- **Нет UI удаления ошибочной записи** → пока правится повторным добавлением с верной суммой (upsert). Удаление — отдельная будущая работа.
- **`YearSelect` сейчас управляется списком лет из данных** → для добавления нужен диапазон лет независимо от наличия записей; при необходимости отдать модалке простой список годов (напр. текущий ± несколько), а не только `availableYears`.

## Migration Plan

Без миграций БД. Чисто аддитивная фича: новый компонент, `action`, хелпер, константа. Откат — удаление кнопки/`action` (данные в `expenses` совместимы с импортом).
